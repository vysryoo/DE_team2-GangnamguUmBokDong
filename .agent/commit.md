# 커밋 메시지 규칙

`AGENTS.md`의 공통 원칙이 이 문서보다 우선한다. type 목록은 `AGENTS.md` 부록을 따른다.

---

## 1. 형식

**커밋 메시지는 제목 한 줄이 전부다.** 본문(body)과 푸터(footer)를 작성하지 않는다.

```
<type>: <한국어 요약>
```

- 제목 아래에 빈 줄이나 추가 내용을 붙이지 않는다.
- 이슈 번호, `Refs:`, `Closes:` 등 트레일러를 붙이지 않는다.
- AI 서명을 붙이지 않는다.

설명이 한 줄에 안 들어간다면 본문을 붙일 게 아니라 **커밋을 더 쪼개야 한다는 신호다.**

---

## 2. 제목 규칙

### 길이

- **70자 이내로 작성한다.** `<type>: ` 접두사를 포함한 전체 길이 기준이다.
- 끝에 마침표를 붙이지 않는다.
- 70자를 넘으면 표현을 줄이지 말고 커밋 분할을 먼저 검토한다.

### Breaking Change

본문을 쓰지 않으므로 `BREAKING CHANGE:` 푸터를 사용할 수 없다. type 뒤에 `!`를 붙여 표시한다.

```
feat!: 주문 조회 응답에서 legacy 필드 제거
```

호환성이 깨지는 변경은 반드시 이 표기를 사용한다. 상세 설명은 PR 본문에서 다룬다.

### 예시

```
좋음: feat: 리프레시 토큰 자동 갱신 로직 추가
좋음: fix: 주문 취소 시 재고 미복구 문제 수정
좋음: refactor: 사용자 조회 쿼리 fetch join으로 변경
좋음: test: 주문 부분 취소 케이스 테스트 추가

나쁨: feat: UserService.java 수정                    (파일명 나열)
나쁨: fix: 버그 수정                                  (내용 없음)
나쁨: feat: 자동 로그인 지원.                          (마침표)
나쁨: chore: 여러 가지 수정 및 리팩터링                (커밋 분할 필요)
```

## 3. 커밋 분할 (Atomic Commit)

**하나의 커밋은 하나의 논리적 변경만 담는다.** 되돌릴 때 그 커밋만 revert해도 말이 되어야 한다.

### 분할 기준

다음이 섞여 있으면 별도 커밋으로 나눈다.

- 서로 다른 type (기능 추가와 리팩터링, 버그 수정과 포매팅)
- 서로 다른 도메인/모듈
- 기능 코드와 그에 딸리지 않은 설정/의존성 변경
- 자동 포매팅으로 인한 대량 변경 (반드시 `style`로 분리)

같은 커밋에 묶어도 되는 것은 다음과 같다.

- 기능 코드와 그 기능의 테스트 코드
- 함수 시그니처 변경과 그로 인한 호출부 수정
- 하나의 동작을 위해 반드시 함께 있어야 하는 변경

### 분할 절차

1. `git status`와 `git diff`로 전체 변경사항을 파악한다.
2. 논리적 단위로 그룹을 나누고, 각 그룹의 제목을 먼저 정한다.
3. 그룹별로 `git add <경로>`로 필요한 파일만 스테이징한다. 한 파일 안에서 변경을 나눠야 하면 `git add -p`는 대화형이라 쓸 수 없으므로, 분할안을 제시하고 사람에게 넘긴다.
4. 각 커밋 직후 `git status`로 의도한 파일만 들어갔는지 확인한다.

### 금지 사항

- **`git add .`, `git add -A`를 사용하지 않는다.** 의도치 않은 파일이 섞인다.
- 커밋 순서상 중간 커밋이 빌드나 테스트를 깨뜨리지 않도록 순서를 잡는다.
- 이미 스테이징된 내용이 여러 논리 단위에 걸쳐 있으면, 임의로 커밋하지 말고 분할안을 먼저 제시한다.

---

## 4. 커밋 전 확인

- 디버깅용 로그, 주석 처리된 코드, 임시 파일이 포함되지 않았는지
- `.env`, 키 파일, 개인 설정 등 커밋되면 안 되는 파일이 섞이지 않았는지
- 스테이징 내용과 작성한 제목이 일치하는지
